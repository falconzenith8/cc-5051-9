# 连续世界探索的分层导航演示

一个零第三方依赖的分层导航演示：远处目的地位于尚未载入精细导航数据的区域时，
系统先用**区域连接关系（粗层）**确定候选门户通道，再**按需真实加载地形块**，
在**精细层**逐段求出角色即将经过的局部路线并推进运动。

## 图形入口（主要使用方式）

本项目的主要入口是浏览器图形界面，所有按钮都调用真实的连续导航实现，
不存在用固定数据冒充的分层路径或分块状态。

```bash
node src/server.js
# 然后浏览器打开 http://localhost:8080
```

可通过环境变量改端口：`PORT=9000 node src/server.js`。

### 图形界面操作

1. 顶部选择**角色半径**（0 = 1×1，1 = 3×3）、**内存预算（驻留块数）**、**加载延迟**。
2. 在地图上：
   - **左键**点击设置起点；
   - **右键**点击设置远程目标（可以点在尚未载入的区域）。
3. 点击 **开始远程求路**：后端立即用粗层门户图给出候选通道（紫色虚线），
   此时精细块尚未加载，地图上对应区域显示为“未载入”。
4. 点击 **单步 Tick** 或 **自动推进**：
   - 精细块按真实异步延迟加载，状态从 `未载入 → 加载中/缺少数据 → 驻留`；
   - 每个块驻留后才运行精细 A*，确认段以绿色实线绘制；
   - 角色只沿已确认的精细路径逐格移动，没有确认路径时原地等待。
5. 程序化近路（粉色门户）在粗层看起来代价最低、会被优先选中，
   但精细层把它砌成墙；规划器检测到 3×3 角色无法通过后**回溯**，
   在粗层排除该门户重新规划，改走有效替代通道。

### 界面如何区分三类信息

| 信息 | 界面表现 |
| --- | --- |
| 暂未搜索（块还没轮到加载） | 分段列表灰色 `暂未搜索`，地图块为虚线“未载入” |
| 缺少数据（加载请求已发出） | 分段列表琥珀色 `缺少数据·加载中`，地图块斜纹“加载中”；**这只是等局部数据，不是不可达** |
| 明确不可达（精细层已验证） | 门户/分段红色，门户序列中加删除线并标注“精细证伪，已回溯”，并在**区域地图**上以红色斜线显示为“已撤销路段” |
| 精细已确认 | 绿色分段与路线，给出精细 A* 代价与扩展节点数 |

右侧面板实时显示：规划状态、粗层尝试次数、分层分段、门户序列、否定信号
（`正在等局部数据` / `已证实不可达`）、渡台席位占用、驻留块清单、驻留字节、
加载/缓存命中/淘汰计数与事件日志。

### 区域存在 ≠ 本次载入的可行边已确认

这是重构后的两个独立概念：

- **区域存在**只由世界登记决定（`world.regionExists`）。因此哪怕目标区域一个
  精细块都没载入，粗层仍能给出候选门户通道，并把它画成紫色**承诺路线**。
- **某次载入的可行边已确认**只在此刻驻留的那一次载入上成立。每条确认都绑定
  载入实例（`instanceId`）；区域被卸载、或同名区域换一组门以新代次重载后，
  旧确认立即失效。地图上据此区分“承诺路线”与“已撤销路段”。

规划器的 `outcome()` 明确返回两种否定信号，调用者不会再把“还在等数据”误当成
“不可达”：`pending-data`（仍在承诺路线上等待）与 `proven-unreachable`（才真正
从承诺路线撤下）。`currentConfirmedPath()` 给出角色当前可安全行走的路段。

### 渡台席位预约

`SeatReservationSystem`（`src/seats.js`）把“某次载入的可行边”表达为一次登台预约：

- 等数据的边持有**候补/已预约**席位，但它不是不可达；
- 精细证伪、卸载区域、撤回指令都会把撤销送到席位系统并真正释放一席；
- **已预约东门班次后，卸载再以同名出口重载，会得到新票、新代次，绝不继承旧位**。

工具条提供 **撤回指令 / 卸载该区（撤出规划）/ 换门重载该区** 三个按钮，
用于观察上述行为；换门重载会让该区域以另一组门连接，两条交叉任务返回时，
实际移动和重新打开的路线都不会借用旧门。

## 架构

```
src/
  rng.js        确定性随机（世界由种子复现）
  world.js      程序化地形块、可核验门户登记、近路精细阻断
  astar.js      网格 A*（带角色占地净空）与通用图 A*
  coarse.js     粗层区域-门户连通图（只读门户登记，不碰精细网格）
  fine.js       精细层块内寻路与门户净空核验（要求块已驻留）
  memory.js     分块存储：异步加载、LRU 淘汰、内存预算、pin、区域载入代次
  seats.js      渡台席位预约：候补/预约/确认/撤销，同名出口不继承旧位
  planner.js    分层规划状态机：粗规划→按需加载→精细确认→回溯修正
  simulation.js 连续运动模拟：逐格推进、pin 当前块、tick 驱动
  server.js     零依赖 HTTP 服务与 REST API
public/         浏览器图形界面（Canvas 渲染 + 真实 API 调用）
```

## 关键设计约束

- **不预载整张导航图**：会话开始时零个精细块驻留，块数据在加载 Promise
  resolve 时才生成并计入内存；未驻留块的接口不返回任何网格。
- **未知区域不是自由空间**：未载入区域只画“未载入”，规划器不能、也无法
  对其做可通行假设；跨块移动只能穿过登记门户且经过精细净空核验。
- **粗层只是候选**：门户在粗层只有身份、几何宽度与代价估计；
  精细层若发现角色尺寸过不去，该门户被标记为明确不可达并触发粗层重搜。
- **角色不踏入无数据块**：角色当前块与所有已确认未走完段涉及的块被
  pin 住，LRU 不会淘汰它们，运动路径逐格与真实网格校验（零穿墙）。
- **区域存在与边确认分离**：粗层只看登记与宏观连通；可行边必须在
  “这一次载入”上确认。同名区域换门重载产生新代次，旧确认与旧席位均作废。
- **等待不是不可达**：`pending-data` 保留承诺路线；只有精细层在本次载入上
  证伪后，边才被撤销并触发粗层回溯。

### 保留旧区域快照 vs 取消后按边重建

改道时有两种处理既有区域数据的办法：

- **保留旧区域快照**：不卸载旧区域，继续沿用其上已确认的边。优点是省去重载；
  代价是旧快照可能已与“这一次载入”不符（例如同名区域换门重载），
  旧确认会被错误地当成当前可行。
- **取消后按边重建（本项目采用）**：撤销旧路线在席位系统里的预约，卸载被放弃
  的区域，并让仍在途的旧细化在完成时被丢弃（载入代次守卫），之后只按
  “当前载入实际登记的门”重新逐边确认。

本项目选择后者：区域存在与边确认分离后，`instanceId` 能把每条确认绑定到某一次
载入。地图上的紫色**承诺路线**是当前粗层候选（含仍在等数据的边），红色斜线
**已撤销路段**才是被证实不可达、从承诺路线撤下的部分。这样“哪一段仍是承诺
路线”与“哪一段已经不可信”在区域地图上一目了然。
